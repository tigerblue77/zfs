## Why

On Linux 5.10 and older, `zvol_open()` reads the `zvol_state_t` from `disk->private_data` and then takes its `zv_state_lock` with nothing holding the zvol in between, and `zvol_os_remove_minor()` relies on `del_gendisk()` to wait for such an opener. That holds on 5.14 and newer (`fops->open()` runs under `disk->open_mutex`, which `del_gendisk()` takes) but not on 5.10 and older, where it runs under the whole disk's `bd_mutex`, which `del_gendisk()` never takes. A fork CI run on AlmaLinux 8 (4.18) panicked this way in `zvol_misc_volmode_race` (`list_del corruption` in `__mutex_remove_waiter()` from `zvol_open()`, in systemd-udevd). The fix `e256741ff14` ("Linux: wait for zvol_open() before freeing a removed zvol") adds a configure check for `bdget_disk()` and `bd_mutex` and, where they exist, takes and drops the whole disk's `bd_mutex` right after `del_gendisk()`, before the zvol can be freed. On 6.12 the check says `no` and the fix compiles out (TASK-1120-ZVO), so only a 5.10 kernel can show both halves.

Route. TASK-1121-ZV510 meant to boot Debian 11's 5.10 on this VM and stopped at step 0 on `orphan_present`. That flag is set by 6.12 at every read-write mount of a journalled ext4 with `orphan_file`, and cleared at a clean unmount or remount-ro, so a mounted root always shows it. Even so, booting 5.10 on this VM carries risks that only the Proxmox console could recover from. Trixie's `mkfs.xfs` makes XFS with `nrext64=1`, which 5.10 cannot mount, so if `/var/tmp` was made that way the boot stops in emergency mode. A crash under 6.12 leaves `orphan_present` set for the next 5.10 boot. And Debian 13's systemd on 5.10 is untried. A Debian 11 guest under QEMU/KVM needs none of that. Its 5.10 kernel is real: Debian's 5.10.0-46 (5.10.262), built with gcc-10, booted with `slub_debug=P`. A panic, a hang or a corrupted guest costs a QEMU restart, not the VM. The trees are built inside the guest, natively for its kernel and userland; this bullseye image is the one upstream's CI boots for `debian11`.

The fix tree is built for the kernel only (`--with-config=kernel`). Its user-space code is master's byte for byte: the fix changes `config/kernel-blkdev.m4` and `module/os/linux/zfs/zvol_os.c` only. So `race.sh` always runs master's `zpool` and `zfs`, against whichever module is loaded, and before each run it checks the loaded module's srcversion against the tree it names.

```python
dev = sys.argv[1]
end = float(sys.argv[2])
n = {"ok": 0, "enxio": 0, "enoent": 0, "other": 0}
while time.time() < end:
    try:
        os.close(os.open(dev, os.O_RDONLY))
        n["ok"] += 1
    except OSError as e:
        if e.errno == errno.ENXIO:
            n["enxio"] += 1
        elif e.errno == errno.ENOENT:
            n["enoent"] += 1
        else:
            n["other"] += 1
print(" ".join("%s=%d" % kv for kv in n.items()))
```
