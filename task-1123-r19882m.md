## Why

- **The failure:** the test zeroes three disks of a raidz3 being expanded (pool exported, reflow paused at offset P), imports it, scrubs, and moves the reflow on. johnpwhite saw one permanent error in 3 of 20 runs on master (1 of 20 on 91bb412, 2 of 20 with #19864).
- **The cause (our 17/11 comment, confirmed by wrouesnel the same day):** a block straddling P is damaged in the new layout below P and in the old layout above it. Once the reflow copies its old rows before the scrub reads it, reconstruction would have to treat 3 current and 3 pre-expansion children as failed; raidz3 allows 3. The export cancels the reflow in the txg sync after a copy cut short by `next_overwrite_blkid`, which can leave P inside a block. At default settings this is rare: wrouesnel had 36 of 36 passes of the stock test, and we saw 0 failures in 60 rounds. **So master may well pass 20 of 20 here; that is not a deviation.**
- This task gives the master baseline with each failure classified. The fix (#19932) is measured elsewhere.

## How `-I 20` iterates

`zfs-tests.sh -t <test>` writes a runfile with one group, the test's directory, whose `pre` and `post` are `raidz/setup` and `raidz/cleanup` (both exist and are executable), with `timeout = 600` per test. `-I 20` is passed to the test runner, which runs that whole runfile 20 times in a row in one process: setup, the test, cleanup, 20 times. So one run gives 60 `Test:` lines, and an all-pass run ends with `PASS 60` in its Results Summary. Each iteration starts from a fresh pool. The runner appends every iteration to `$R/log` (result line first, then the test's timestamped output), but the test's own `stdout`/`merged` files under `$R` are overwritten by each iteration, so read `$R/log` only.

## Classifying failures (the callback)

The test does not log P on master (`reflowed` in its notes is bytes copied, not an offset) and it destroys the pool in its cleanup, so a failure cannot be classified afterwards. The test's `log_fail` runs the scripts listed in `TESTFAIL_CALLBACKS` **before** the test's cleanup, inside the test's process (root, through the runner's `sudo -E`), with the pool still imported. This task adds one such script, outside the tree, ahead of the three default ones. It changes nothing in the pool. It prints, each line prefixed with `r19882-cb`:
- `P:` the last `raidz_reflow_info` lines of `zfs_dbgmsg`, which `spa_load` writes at every import (`uberblock raidz_reflow_info: state=N offset=P`): the last one is the P of the failing round's import, the boundary between the two layouts that the damage met;
- `E:` the `errors:` section of `zpool status -v testpool`;
- for each file listed there: `F:` its path, dataset and object number, then `B:` the `L0` lines of `zdb -e -ddddd <dataset> <object>`, whose DVAs read `0:<offset>:<asize>` in hex.

A block straddles P when `offset < P < offset + asize`. The datasets are `fs` and `fs2` (100K files, one 100K block each) and `fs3` (8K records, 13 blocks per file).
