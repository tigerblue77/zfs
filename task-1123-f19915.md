## Why

- **The bug:** on a full pool, or on a file system at its `refquota`, `fsync(2)`, `fdatasync(2)` and `msync(MS_SYNC)` on a file with dirty mmap'd pages return 28 (ENOSPC) or 122 (EDQUOT) with errno 0, instead of -1 with errno set. `zpl_putpage()` (`module/os/linux/zfs/zpl_file.c`) passes on `zfs_putpage()`'s positive errno, and `zpl_fsync()` returns it to the VFS unchanged. On kernels where `write_cache_pages()` is built on `writeback_iter()` (6.12 is one), the positive value also trips `WARN_ON_ONCE(*error > 0)` there.
- **Baseline already seen here (TASK-1123-IS3, VM 105, Linux 6.12.118, master `a1daebfec3f`):** fsync and msync returned +28 on a full pool and +122 at a refquota, errno 0, and 0 with free space; the kernel printed the `WARN_ON_ONCE` at `mm/page-writeback.c:2572` in `writeback_iter` from `write_cache_pages` ← `zpl_fsync` ← `do_fsync`.
- **The fix:** `zpl_putpage()` negates the value and asserts `ret <= 0` (the reporter's proposal). Every kernel path to `zfs_putpage()` goes through it.
- **The test** `mmap_sync_error` (mmap group, Linux runfile) with its helper `mmap_sync_error <file> 0|ENOSPC|EDQUOT`: a pool `testpool1` on a 256 MiB file vdev `/var/tmp/mmap_sync_error.vdev`, mounted at `/var/tmp/testdir1`, an 8 MiB file `fs/file`. The helper stores into every page of a shared mapping of the file, then calls `fsync`, `fdatasync` and `msync(MS_SYNC)` in turn (storing again before each), prints `<call>: returned <n>, errno <e> (<text>)` for each, and exits 1 unless each returned what was expected. Order: refquota set to `referenced` → expect EDQUOT; refquota removed → expect 0; pool filled with two `dd` passes until ENOSPC → expect ENOSPC; fill files removed → expect 0.
