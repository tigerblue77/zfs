## Why

The leak. From Linux 4.16 to 5.10, `__blkdev_get()` (`fs/block_dev.c`) takes a reference on the gendisk and on its driver's module (zfs) on each pass of an open, and keeps them only for the first opener of the device: `if (!first_open) put_disk_and_module(disk);`. It sets `first_open` on a pass that finds `bd_openers` at 0, and does not clear it when `fops->open()` returns `-ERESTARTSYS` and it goes back to `restart:`. If another task opens the device before the restarted pass takes the disk's `bd_mutex`, that pass finds the device open, `zvol_open()` succeeds (the zvol is open, so it needs no namespace lock), and its references are never put: one zfs module reference per occurrence, held until the machine stops. On 5.12 and older, master's `zvol_open()` returns `-ERESTARTSYS` at once when a first open cannot take `spa_namespace_lock` (configure: `whether blkdev_get_by_path() handles ERESTARTSYS... yes`). ZV510C saw it in this same guest: under `race.sh`, with a tree whose `zvol_open()` is master's, the zfs module's use count rose 0, 1, 1, 3 across the runs, and `rmmod` then refused (`Module zfs is in use`). Linux 5.11 reworked `__blkdev_get()`: there every open holds its own references.

The branch's change, in `module/os/linux/zfs/zvol_os.c`: `zvol_open()` waits for the lock for up to `zvol_open_timeout_ms` (1000 ms, in 10 ms steps) on every kernel, as it already did on 5.13 and newer, and only then returns `-ERESTARTSYS`. While it waits it holds `bd_mutex`, so the other openers of the device wait in `__blkdev_get()` before they reach the first-open path, instead of restarting next to it. `zvol_open_timeout_ms` becomes a module parameter on 5.10 too (on master it exists only from 5.13): on 5.10 that parameter is what tells the two modules apart. The branch also documents the parameter in `zfs.4`. ZV510D tests the same `zvol_os.c` change under `race.sh`, on top of the M-41 fix; this task tests the pull request's own branch, on master, through its regression test, and does not depend on ZV510D's outcome.

The test, `zvol_misc_open_contended` (Linux only; it skips with `log_unsupported` on 5.11 and newer). It creates a zvol (`testpool/openvol`, 16M) and a second pool `testpool1` on a file in its work directory under `/var/tmp`, sets `zvol_open_timeout_ms` to 60000 where the parameter exists, reads the zfs module's use count (`/sys/module/zfs/refcnt`, the lowest of four reads), delays every write to `testpool1` by one second (`zinject -D 1000:64 -T write`), and runs `zpool reguid testpool1`, which holds `spa_namespace_lock` while it waits for a txg sync (at least four seconds with the delay). One second in, four processes open the zvol and each keeps it open for three seconds. One second later it checks that `zpool reguid` is still running, that the four openers have started and that none has opened the zvol. Then every open must succeed, and the use count, read again for up to 30 s, must be back to its value before the opens. The value before is not 0: the group's setup creates `testpool`, whose mounted root file system holds one reference, so it is about 1.

Expected on `m` (master and the test): every opener restarts while the lock is held, so each has `first_open` set; once the lock is released one opens the zvol and the three others find it open, and each keeps a reference: the count rises by 3 in one pass, without a loop. The test fails with `The zfs module's use count rose from <N> to <N+3>` in about 50 s (30 s of it the re-reads). The group's clean-up then destroys `testpool`, and the three references stay: a use count of 3 with no pool, zvol, mount or open file, and `rmmod` refuses. On master the parameter does not exist on 5.10 (it is compiled out where `HAVE_BLKDEV_GET_ERESTARTSYS` is defined), and the test leaves it alone (`tunable_exists` reads the sysfs file; `save_tunable` and `restore_tunable` then do nothing): the test runs as written. Expected on `f` (the branch): the first opener waits in `zvol_open()` holding `bd_mutex` until the lock is free, the three others wait for `bd_mutex`, nobody restarts; PASS in about 20 s, the count unchanged, a use count of 0 after the run, and a clean unload.

One boot per master run. A leaked reference cannot be dropped: the module stays loaded until the guest powers off, so it can neither be unloaded nor reloaded. A second master run in the same boot would start from a module that has already leaked, which no CI run sees, and the use count is the verdict. So each master run gets its own fresh boot (B3, B4, B5, about 8 minutes each), and three of them show whether the failure is reliable: the test makes every opener restart while the lock is held, so the rise is expected each time, not by chance. The branch's runs share one boot (B2): each is followed by an unload, which must succeed, and a reload, so that each of them both starts from a fresh module and ends with a clean unload. The branch goes first: if its runs show that the test's hold does not work in this guest, the master boots would only repeat that (step 7 then runs one of them).

`-T zvol_misc` once on `f`: 13 tests (8 from `common.run`, 5 from `linux.run`, the new one included) and the two groups' setup and cleanup, 17 results; ZOT ran the same group on 6.12 (with its own new test in place of this one): 17 PASS in 3 min 10. On 5.10 this tree lacks the M-41 fix `e256741ff14` (a separate branch, `zvol-open-pin-state`): `zvol_misc_volmode_race`, or any test that removes a minor while udev opens it, can hit M-41's use-after-free in `zvol_open()` (a `general protection fault` at a `0x6b6b...` address in `__mutex_lock()` from `zvol_open()`, a `list_del corruption`, or a SLUB `Poison overwritten`). The window is narrow (fork CI hit it once on AlmaLinux 8; ZV510C needed `race.sh` and 164 s to see it on master), and master has it too: such a finding is reported as M-41, not against this branch.
