## Why

- **The failure:** the test zeroes three disks of a raidz3 being expanded (pool exported, reflow paused at offset P), imports it, scrubs, and moves the reflow on. johnpwhite saw one permanent error in 3 of 20 runs on master.
- **The cause (our 17/11 comment, confirmed by wrouesnel the same day):** a block straddling P is damaged in the new layout below P and in the old layout above it. Once the reflow copies its old rows before the scrub reads it, reconstruction would have to treat 3 current and 3 pre-expansion children as failed; raidz3 allows 3. At default settings P rarely falls inside a block; with `raidz_expand_max_copy_bytes=4096` it often does (on master + #19864, 18 of 30 rounds lost exactly the block at P, and the test failed 5 of 5).
- **The fix (#19932):** the test reads P from the exported pool's uberblock (`zdb -e -p <devdir> -u`), checks it, and zeroes each of the three disks only over child MiB `[0, lo)` (new layout, below P - 512K) and `[hi, end)` (old layout, at or above P + 512K), leaving the band around P intact, so a straddling block is damaged on one side only. It logs, every round, `reflow offset P, damaging MiB [0, lo) and [hi, end)`. Its own checks `log_fail` with `invalid reflow offset in the uberblock: ...` or `invalid damage bounds: ...`; either is a failure of the fix's own code. The PR also moves the test's file vdevs into `/var/tmp/raidz_expand_scrub_repair/dev-0` to `dev-6` and creates the pool with `ashift=9`.
- **So:** 20 of 20 PASS is expected at default settings, and the stress pass, which puts P inside blocks, must pass too: its 5 iterations are 15 rounds where the band is what saves the straddling block.

## How `-I` iterates

`zfs-tests.sh -t <test>` writes a runfile with one group, the test's directory, whose `pre` and `post` are `raidz/setup` and `raidz/cleanup` (both exist and are executable), with `timeout = 600` per test. `-I N` is passed to the test runner, which runs that whole runfile N times in a row in one process: setup, the test, cleanup, N times. So `-I 20` gives 60 `Test:` lines and an all-pass run ends with `PASS 60` in its Results Summary; `-I 5` gives 15 and `PASS 15`. Each iteration starts from a fresh pool. The runner appends every iteration to `$R/log` (result line first, then the test's timestamped output), but the test's own `stdout`/`merged` files under `$R` are overwritten by each iteration, so read `$R/log` only.

## Classifying failures (the callback)

The test destroys the pool in its cleanup, so a failure cannot be classified afterwards. The test's `log_fail` runs the scripts listed in `TESTFAIL_CALLBACKS` **before** the test's cleanup, inside the test's process (root, through the runner's `sudo -E`), with the pool still imported. This task adds one such script, outside the tree, ahead of the three default ones. It changes nothing in the pool. It prints, each line prefixed with `r19882-cb`:
- `P:` the last `raidz_reflow_info` lines of `zfs_dbgmsg`, which `spa_load` writes at every import (`uberblock raidz_reflow_info: state=N offset=P`): the last one is the P of the failing round's import. It must equal the P of that round's `reflow offset` NOTE line;
- `E:` the `errors:` section of `zpool status -v testpool`;
- for each file listed there: `F:` its path, dataset and object number, then `B:` the `L0` lines of `zdb -e -p /var/tmp/raidz_expand_scrub_repair -ddddd <dataset> <object>`, whose DVAs read `0:<offset>:<asize>` in hex.

A block straddles P when `offset < P < offset + asize`. The datasets are `fs` and `fs2` (100K files, one 100K block each) and `fs3` (8K records, 13 blocks per file).
