## Why

`vdev_raidz_io_start()` (master) maps an i/o to an expanding RAID-Z vdev with the reflow offset in `spa_ubsync`: rows below it use the new location, rows above it the old one (plus the new one for writes where the copy has started). `raidz_reflow_sync()` commits the progress of a txg into `spa_uberblock` under the expansion range lock, but `spa_sync()` copies `spa_uberblock` into `spa_ubsync` only at its very end, so an i/o that starts in between maps the committed rows to their old location. Once `spa_ubsync` has advanced, `raidz_reflow_impl()` lets the reflow copy data whose new location is that old location; an i/o from the window still in flight then reads other data (or, for a write, overwrites data the reflow has just placed there). The fix (`module/zfs/spa.c`, the end of `spa_sync()`) takes the range lock as a writer over `[synced offset, committed offset)` while it updates `spa_ubsync`, so that the update waits for those i/os.

- test (commit 5, 0d50fb4352ef188fb5d626a066ed5f19846c1fb5, on N-01's four commits): adds two zinject points. `raidz_reflow_sync:committed` (end of `raidz_reflow_sync()`, syncing context, once the progress of the txg is in `spa_uberblock`) and `vdev_raidz_io_start:copied` (in `vdev_raidz_io_start()`, only for an i/o overlapping `[spa_ubsync offset, vre_offset)`, after it took the range lock as a reader and read the offsets, before it maps the rows). The test `raidz_expand_inflight_read`: a raidz1 of six 256 MiB files, ashift 12, `zfs_vdev_min_ms_count` 2 (512 MiB metaslabs), `zfs_prefetch_disable` 1, `zfs_scrub_after_expand` 0; a 200 MiB random file with recordsize 128K, compression off, primarycache=metadata, atime off; attach a seventh file with `raidz_expand_max_reflow_bytes` at allocated/20; export, read the on-disk reflow offset (`zdb -u`) and pick the first L0 block of the file past it (it must end before offset + (offset/4K/6 - 6)*4K, the progress the next txg will commit); import, read the block once, raise `zfs_txg_timeout` to 600, hold the next sync at the first point while the reflow resumes, read the block in the background and hold the read at the second point, set the reflow free and release the sync, poll `reflowed` for up to 20 s until it reaches 3/2 of the end of the block, release the read. It fails if any vdev then shows checksum errors, reports UNSUPPORTED if anything other than the read was held at the second point, compares the block, lets the expansion finish, scrubs (`repaired 0B`, no errors) and checks the file digest.
- fail-before (commit 6, 1c24319aa00118d675b8a325fe984e7b7f33a896): `git revert` of `c9e0d4c8934` on top of the test, `module/zfs/spa.c` only (1 insertion, 18 deletions).
