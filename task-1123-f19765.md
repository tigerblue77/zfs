## Why

- **The bug** (reproduced by TASK-1123-IS4 on VM 106, master `a1daebfec3f`, with the reporter's workload: the first `zfs rollback` hung, SysRq reboot): `zpl_fadvise()` holds the dataset's teardown lock as reader across `generic_fadvise()`, which for `POSIX_FADV_DONTNEED` writes the file's dirty pages out and waits for each page's lock. The flusher locks such a page, then waits in `zfs_putpage()` for the teardown lock; once a writer (a rollback, a forced receive, a property set that takes the lock as writer) waits for that lock, no new reader gets in. The writer waits for fadvise, fadvise for the page, the flusher for the writer, and the dataset stays frozen until a reboot.
- **The fix** (`module/os/linux/zfs/zfs_vnops_os.c`): `zfs_putpage()` unlocks the page before it enters the file system. It already unlocked it (redirtied) before taking the range lock and checked it again once relocked; now no writeback waits for the teardown lock with a page locked, which is the order every other path follows.
- **The test** `fadvise_dontneed_teardown` (fadvise group, Linux runfile): a 64 MiB file, a writer dirtying random pages of it through a shared mapping, four advisers looping `open`/`posix_fadvise(DONTNEED)`/`close`, `sync -f` every 20 ms, and `zfs set defaultuserquota` (teardown lock as writer) in a loop for 30 s; each set must return within 30 s, else the test fails and its cleanup leaves the dataset alone. It uses a property set and not a rollback because a rollback's `zfs_resume_fs()` drops the file's pages with the lock held, which can deadlock on its own with page faults (the page-fault side of #19764's cycle, which this fix does not remove) and would make the test hang on the fix too.
- **Expected:** zd: the test passes, each set returning in a few seconds at most; the groups pass. zf: the test fails at its 30 s bound, the dataset wedged with the three tasks of the cycle above.
